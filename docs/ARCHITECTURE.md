# معماری پروژه

این سند توضیح می‌دهد سیستم از داخل چطور کار می‌کند: مدل داده، مسیر یک درخواست RAG،
مدل امنیتی/RBAC، و نحوه‌ی کار ویجت جاسازی‌شده. برای فهرست کامل endpointها به
[API.md](./API.md) و برای دید کلی/نصب به [README.md](../README.md) اصلی مراجعه کن.

## ۱. نمای کلی معماری

```
                         ┌─────────────────────────────┐
                         │   frontend/ (استاتیک)       │
                         │   index / dashboard / admin  │
                         │   widget.js (Shadow DOM)      │
                         └───────────────┬───────────────┘
                                          │ fetch (JWT Bearer)
                                          ▼
┌────────────────────────────────────────────────────────────────┐
│                     FastAPI  (app/main.py)                      │
│                                                                  │
│  routers/auth        → ثبت‌نام، ورود، JWT                        │
│  routers/settings     → اتصال مدل + شخصی‌سازی RAG/پرامپت         │
│  routers/knowledge    → CRUD دانشنامه + ایندکس‌کردن               │
│  routers/playground   → تست چت RAG، جست‌وجوی معنایی، Battle       │
│  routers/widget       → تنظیم ظاهر ویجت + تولید کد Embed          │
│  routers/public_widget→ (بدون احراز هویت) چت عمومی ویجت           │
│  routers/admin        → RBAC، آمار، مدیریت کاربران، امنیت         │
│                                                                  │
│  services/llm_client   → پُل ارتباط با هر سرویس OpenAI-Compatible │
│  services/rag_store     → فروشگاه برداری سبک (SQLite + cosine)   │
│  services/rag_pipeline  → orchestration کامل یک چرخه‌ی RAG        │
│  services/text_split    → تکه‌تکه‌کردن اسناد                      │
│  services/injection_scanner → تشخیص heuristic تزریق پرامپت        │
  services/rate_limit        → محدودکننده نرخ ویجت عمومی          │
└───────────────────────────────┬──────────────────────────────────┘
                                 │ SQLAlchemy ORM
                                 ▼
                    ┌─────────────────────────┐
                    │   SQLite (data/app.db)   │
                    │  users / settings /      │
                    │  documents / chunks /     │
                    │  chat_sessions / messages │
                    └─────────────────────────┘
                                 │
                                 ▼ (فقط وقتی provider پیش‌فرض/سفارشی فراخوانی می‌شود)
                    ┌─────────────────────────────┐
                    │  هر سرویس OpenAI-Compatible   │
                    │  (پیش‌فرض: RaCode LLM یا       │
                    │   کلید اختصاصی خود کاربر)      │
                    └─────────────────────────────┘
```

هم داشبورد کاربر، هم پنل ادمین، هم API عمومیِ ویجت، همگی از **یک** پردازه‌ی
FastAPI سرو می‌شوند — فرانت‌اند به‌صورت فایل استاتیک توسط همان اپلیکیشن سرو
می‌شود، بنابراین برای اجرای کامل پروژه فقط یک سرور لازم است (`setup.bat`).

## ۲. مدل داده

| جدول            | نقش                                                                 |
|------------------|----------------------------------------------------------------------|
| `users`          | حساب کاربری (نام کاربری، نقش user/admin، وضعیت مسدود/فعال)           |
| `user_settings`  | ۱-به-۱ با کاربر: اتصال مدل، پرامپت سیستمی، پارامترهای RAG، ظاهر ویجت |
| `documents`      | اسناد خام دانشنامه‌ی هر کاربر                                        |
| `chunks`         | تکه‌های ایندکس‌شده‌ی هر سند + بردار امبدینگ (JSON)                    |
| `chat_sessions`  | یک نشست گفت‌وگو؛ `source` مشخص می‌کند از «آزمایشگاه تست» بوده یا «ویجت عمومی» |
| `chat_messages`  | پیام‌های هر نشست + پرچم مشکوک‌به‌تزریق (`is_flagged`, `flag_reason`)  |

**ایزوله‌سازی داده بین کاربران:** هر پرس‌وجو به `documents`، `chunks` و
`chat_sessions` همیشه با `user_id == current_user.id` فیلتر می‌شود (چه در
مسیرهای داشبورد، چه در پنل ادمین که صراحتاً `user_id` هدف را از مسیر URL
می‌گیرد). هیچ کوئری «همه‌ی چانک‌ها»ی بدون فیلتر کاربر وجود ندارد.

## ۳. چرخه‌ی یک درخواست RAG (`services/rag_pipeline.py`)

هم «تست چت RAG» در داشبورد و هم چت عمومیِ ویجت از **همین** تابع مشترک استفاده
می‌کنند تا رفتار دو محیط همیشه یکسان بماند:

1. تنظیمات ارائه‌دهنده‌ی مدل کاربر resolve می‌شود (`llm_client.resolve_provider`):
   اگر کاربر کلید اختصاصی خودش را فعال کرده باشد از آن، وگرنه از ارائه‌دهنده‌ی
   رایگان پیش‌فرض (`DEFAULT_PROVIDER_*` در `.env`) استفاده می‌شود.
2. پیام کاربر با مدل Embedding امبد می‌شود.
3. `rag_store.search` در بین چانک‌های همان کاربر (فقط همان کاربر) با
   cosine similarity جست‌وجو می‌کند، نتایج زیر `similarity_threshold` را کنار
   می‌گذارد و سپس بهترین `top_k` تکه را برمی‌گرداند.
4. تکه‌های بازیابی‌شده به‌عنوان context داخل پرامپت سیستمیِ شخصی‌سازی‌شده‌ی
   کاربر تزریق می‌شوند.
5. تاریخچه‌ی همان نشست (حداکثر ۱۲ پیام و سقف ۱۲هزار کاراکتر) قبل از پیام جدید
   به لیست messages اضافه می‌شود تا هم پیوستگی حفظ شود و هم prompt بدون حد رشد نکند.
6. پاسخ از مدل چت گرفته می‌شود؛ پیام کاربر و پاسخ دستیار در دیتابیس ذخیره
   می‌شوند و پیام کاربر همزمان از اسکنر تزریق پرامپت عبور می‌کند.

## ۴. احراز هویت، نقش‌ها و مسدودسازی

- ورود، JWT کوتاه با `sub=user_id` صادر می‌کند (`security.py`).
- `get_current_user` روی هر مسیر محافظت‌شده، توکن را می‌خواند، کاربر را از
  دیتابیس می‌گیرد، و اگر `is_active=False` باشد **بلافاصله ۴۰۳** برمی‌گرداند —
  یعنی مسدودسازی توسط ادمین، همان لحظه هم پنل کاربر و هم API عمومیِ ویجتش را
  غیرفعال می‌کند (چک مشابه در `routers/public_widget.py` هم تکرار شده).
- مسیرهای بدون توکن → **۴۰۱** (خودکار توسط `OAuth2PasswordBearer`).
- مسیرهای ادمین (`require_admin`) با توکن معتبرِ نقش غیر-ادمین → **۴۰۳**.
- **ورود به‌جای کاربر (Impersonation):** ادمین یک JWT جداگانه با claim اضافه‌ی
  `impersonated_by` و عمر کوتاه (۳۰ دقیقه) می‌گیرد. فرانت‌اند توکن ادمین را در
  `localStorage` کنار می‌گذارد (stash)، با توکن جدید وارد داشبورد همان کاربر
  می‌شود، و با دکمه‌ی «بازگشت به پنل ادمین» توکن اصلی برمی‌گردد.

## ۵. مدل امنیتی ویجت عمومی

`routers/public_widget.py` هیچ احراز هویتی نمی‌خواهد (بازدیدکننده‌ی ناشناس
یک سایت شخص‌ثالث است)، ولی:

- کاربر فقط از طریق `widget_id` (یک UUID غیرقابل‌حدس، مستقل از JWT/شناسه‌ی
  داخلی کاربر) شناسایی می‌شود — هیچ اطلاعات حساسی (کلید API، JWT) هیچ‌وقت به
  مرورگر بازدیدکننده فرستاده نمی‌شود.
- اگر صاحب ویجت مسدود باشد، endpoint چت بلافاصله ۴۰۳ برمی‌گرداند.
- CORS به‌صورت عمدی باز (`allow_origins=["*"]`) است چون ویجت باید از هر
  دامنه‌ی شخص‌ثالثی قابل‌فراخوانی باشد.
- CSS/JS ویجت داخل **Shadow DOM** رندر می‌شود تا با استایل‌های سایت میزبان
  تداخل نداشته باشد.
- endpoint چت عمومی با یک rate limiter درون‌پردازشی محدود می‌شود؛ این فقط یک
  کنترل سوءاستفاده‌ی پایه است و برای چند instance باید با storage مشترک جایگزین شود.

## ۶. Prompt Injection Watch

طبق سند پروژه، این بخش عمداً ساده (heuristic/regex) پیاده‌سازی شده
(`services/injection_scanner.py`) نه یک مدل امنیتی کامل. هر پیام ورودیِ
کاربر/بازدیدکننده با چند الگوی رایج فارسی/انگلیسی چک می‌شود؛ در صورت تطابق،
پیام با `is_flagged=True` و دلیل تشخیص ذخیره می‌شود و در پنل ادمین → «نظارت
امنیتی» برای بازبینیِ دستی قابل‌مشاهده است.

## ۷. خطا، مشاهده‌پذیری و عملیات

- `AppError` خطاهای قابل‌پیش‌بینی را به پاسخ‌های استاندارد API تبدیل می‌کند.
- exceptionهای غیرمنتظره در لاگ ثبت می‌شوند ولی متن خام آن‌ها به کلاینت برنمی‌گردد.
- middleware برای هر درخواست یک `X-Request-ID` تولید و زمان پاسخ را log می‌کند.
- داشبورد کاربر از `/api/dashboard/summary` آمار scoped دریافت می‌کند.
- عملیات reindex دانشنامه مستقل از ویرایش محتوا در دسترس است.
- حذف نشست آزمایشگاه فقط برای owner همان نشست مجاز است.

## ۸. جایی که پیاده‌سازی از پشته‌ی *پیشنهادی* فاصله گرفته (و چرا)

سند پروژه صراحتاً می‌گوید پشته‌ی فناوری «کاملاً پیشنهادی» است و الزامی به
استفاده از آن نیست. برای یک دموی قابل‌اجرا با یک کلیک روی `setup.bat`، سه
انتخاب آگاهانه جایگزین شدند:

| پیشنهاد سند         | چیزی که پیاده شد                | چرا                                                                 |
|----------------------|----------------------------------|-----------------------------------------------------------------------|
| ChromaDB             | فروشگاه برداری سبک روی SQLite + numpy (`rag_store.py`) | ChromaDB به SQLite نسخه‌ی بالا و وابستگی‌های سنگین‌تر (onnxruntime و…) نیاز دارد که نصبش روی ویندوزهای مختلف می‌تواند شکننده باشد؛ در مقیاس یک دمو (چند صد–چند هزار چانک) cosine similarity در حافظه به همان اندازه سریع و «Embedded/بدون سرور جداگانه» است. |
| bcrypt/passlib       | `hashlib.pbkdf2_hmac` استاندارد پایتون | هیچ وابستگی کامپایل‌شونده‌ی اضافه‌ای نصب نمی‌شود؛ نصب روی ویندوز همیشه بدون خطا موفق است. |
| Alembic              | `Base.metadata.create_all()` در startup | برای یک پروژه‌ی تک‌نسخه‌ای/دمو، migration tracking سربار اضافه بدون فایده‌ی عملی است؛ اگر پروژه ادامه پیدا کند، افزودن Alembic روی همین مدل‌ها ساده است. |

همه‌ی این‌ها فقط جزئیات پیاده‌سازی داخلی‌اند؛ تمام رفتارها و نیازمندی‌های
عملکردیِ خواسته‌شده در سند (شامل «Embedded بودن»، «بدون نیاز به راه‌اندازی
سرور جداگانه» و غیره) حفظ شده‌اند.
